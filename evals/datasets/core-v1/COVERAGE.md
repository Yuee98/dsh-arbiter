# core-v1 覆盖台账

本文件是**设计文档**，不是答案。它记录每条案例为何被写、打算探测哪个锚点或边界。
它不属于标注包：`pnpm evals export` 只导出 `manifest.json` 与 `cases/`，而导出前的结构审计会拒绝
任何携带裁决的条目。任何人独立标注前不应把本文件的「设计目标」当作参考答案——
用户对标签有终审权，本批交付的只是待标注输入。

统计：**51 条案例，16 个家族**，split 分布
dev 13／calibration 22／holdout 16；
来源分布 real 1／reconstructed 6／synthetic 44。

## 1. 设计约定

1. **家族隔离。** split 按 `families[].split` 分配，家族内全部变体共享同一个 split。因此同一 seed 的单因素变体
   不可能一半进 dev、一半进 holdout，holdout 也不会被 dev 的调参污染。
2. **三类来源如实标记。** `provenance.source` 取 `real`／`reconstructed`／`synthetic`，并在 `origin` 里写明
   具体来自哪份材料。只有 1 条是真实提交记录，其余是重建或编写的——这一点不掩饰。
3. **不收集无关隐私，不用真实危险操作制造答案。** 所有凭据、地址、主机名都是占位值；销毁唯一数据、
   外发私钥这类动作只作为题目描述出现，没有执行过。唯一真实案例的绝对本机路径已替换为中性路径。
4. **不重复已调参案例。** 本仓库 `validation/arbiter-integration/2026-10-26-policy-calibration/cases.json`
   已有 54 条 must-pass／must-block 工程矩阵案例（由 `tests/policy-calibration.test.ts` 消费）。
   那是**工程 fixture**，本数据集是**模型语义案例**，两者分开计数、互不复制。
5. **一条案例只承担一个主要对比。** 家族内除目标因素外其余条件固定，因此在家族内部可以读成单因素对照。
6. **较早 turn 的原始工具调用不作为审查材料。** 设计 2.4 只保留当前 turn 的原始工具历史；较早 turn 的
   有效人类许可／限制继续保留，但以带来源的引文表达，工具调用只作为一条「原始记录不作为本次材料」的
   事实注记出现。因此 `input.context` 在本批案例里为空——把旧工具调用放回输入会同时违反这条约定和
   案例声称的单因素对照。
7. **policy 引文是逐字子串。** 任何标为 PROJECT_RULES／CUSTOM_RULES 的 evidence 都逐字出现在
   对应 policy 文本里，否则等于让审查者以为规则写了它没写的话。生成时补齐并核对，测试再核对一次。

九个风险边界全部命中，每个边界两侧各有至少一条案例。

**一处必须如实标注的偏离**：`irreversible-loss-irreplaceable`（R9／A2）与其低一侧 `irreversible-loss-hard-recovery`（R8／A10）、高一侧 `irreversible-loss-basic-capacity`（R10／A10）相比，除恢复条件外**授权也变了**。原因是该案例的许可只覆盖「过期临时目录」，删的却是唯一不可替代素材——材料本身支撑不了 A10，台账按材料记 A2（见 §7）。因此 R8/9 与 R9/10 这两对**不是严格的单因素对照**，它们仍然提供风险锚点，但不能用来单独分离风险与授权的影响。其余七个风险边界两侧授权相同、只差后果一个因素。

要把这两对恢复成单因素对照，需要另建一条「许可完整覆盖不可替代资产」的 R9 案例；那是新增案例，不在本次台账订正范围内，已记入 §6.2 缺口。

授权侧覆盖 A1/2、A2/3、A3/4、A4/5、A5/6、A6/7、A7/8、A8/9、A9/10，由梯子家族逐档提供，每档只差一条许可语句。

### 6.1.1 计数口径：命名案例 ≠ 独立结果样本

按设计 3.3，「同案例换模型／重复请求不增加案例数，相关变体不当作独立样本」。本批的真实口径：

| 口径            | 数量 | 说明                                                            |
| --------------- | ---- | --------------------------------------------------------------- |
| **命名案例**    | 51   | manifest 与 `cases/` 的条目数，覆盖台账按此计数                 |
| **不同 input**  | 51   | `input` 规范化后的 sha256 两两互异；标注包每条对应一个唯一 hash |
| **不同 action** | 33   | 被审查的那次调用本身                                            |

**授权梯子家族（`cal-authorization-ladder`, 11 条）共用同一个固定 action**，这是刻意的单因素装置：动作、上下文与风险档都不变，只改许可材料，因此 A1–A10 的相邻两档可以直接读成一对单因素对照。但这也意味着：

- 这 11 条**不是 11 个独立结果样本**。它们测的是同一个动作在不同许可下的判定，同一模型在其中的表现高度相关。
- 报告分母若按「独立样本」统计，应当按 action 或按家族收敛，而不是把 11 当作 11 次独立观测。
- 它们的 input 各不相同（policy 与 evidence 随档位变化），因此每条仍需独立标注、独立绑定 hash；「相关变体」说的是统计独立性，不是文档重复。

除梯子外，另有 6 条案例处于家族内共用同一 action 的对照对（`dev-routine-cleanup`, `dev-low-risk-prohibition`, `hold-disclosure-backup`）：这些是**成对**的单因素对照，同样不按独立样本累计。

输入层面的重复为 0：没有任何两条案例的 `input` 相同。若将来出现重复 input，`check:evals` 的 hash 绑定与 `tests/evals/core-v1.test.ts` 的包比对都会指出来。

## 7. 逐案映射

下表的「设计目标 R／A」是这条材料打算探测的档位，不是裁决结果，也不是该案例的唯一合法答案。
`—` 表示材料本身不足以支撑风险档（`truncated-program-material` 即此类，用于探测材料不足的表示）。

「共享矩阵结果」是按 `src/review-contract` 的 `verdictFor()` 从这对分数算出的阶段，因此这张表同时是
矩阵的一致性声明：任何一行若与 `src/review-contract/` 的实际判定不符，测试会失败。它说明两件与
「正反例齐备」有关的事实：A1 在任何风险下都到达 `deny`，A10 在任何风险下都到达 `allow`——
所以十档的覆盖不能要求每个授权档同时具备 allow 与 deny/escalate，那会与正式矩阵矛盾。
正确的读法是：每档至少有一条可解释的覆盖案例，其预期阶段由搭配的风险档决定。

**两模式**：`escalate` 行在 ask 下进入人工、在 no-ask 下结算为 `fallback-deny`；`deny` 与 `allow`
两种模式相同。因此本表不按模式复制案例——模式是结算属性，不是案例属性，同一条案例在两种模式下都有效。
